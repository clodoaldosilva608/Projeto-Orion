   157→**Feature Detail: IA Básico**
   158→
   159→- **Descrição:** Sistema de IA que permite aos usuários fazer perguntas em linguagem natural sobre seus dados ("Quantos vendedores bateram a meta em outubro?"), recebe insights automáticos diários ("João está 15% abaixo da meta, sugerir acompanhamento"), prevê meta mensal baseado em tendência, e gera relatório narrativo semanal.
   160→- **Esforço:** 120 story points (~6 devs × 4 semanas)
   161→- **Dependências:** v1.0 completo (metas, resultados, ranking)
   162→- **Stack:** OpenAI GPT-4o-mini (custo otimizado), pgvector para embeddings, Redis para cache
   163→- **Métricas:**
   164→  - Latência p95 chat: < 3s
   165→  - Custo por query: < R$ 0,15
   166→  - Satisfação (thumbs up/down): > 75% positivo
   167→  - Adesão: 60% das empresas ativas usam IA no mês
   168→- **Riscos:**
   169→  - Custo de IA explode → mitigar com cache agressivo + fallback para GPT-3.5
   170→  - Alucinação → mitigar com prompt engineering + RAG com dados estruturados
   171→  - LGPD → dados pessoais NUNCA enviados à IA (anonimização prévia)

   643→
   644→Tech debt é inevitável em startup de crescimento rápido. A estratégia é **reservar 20% da capacidade de cada sprint para tech debt** e ter um roadmap explícito de pagamento.
   645→
   646→## 10.1 Tech Debt Identificado (Q4 2025)
   647→
   648→| ID | Descrição | Severidade | Esforço | Prazo |
   649→|----|-----------|------------|---------|-------|
   650→| TD-001 | Auth usa NextAuth; migrar para solução própria para suportar refresh token rotation | Alta | 60 SP | Q1 2026 |
   651→| TD-002 | Sem particionamento em `results` (table scan em relatórios mensais) | Alta | 80 SP | Q1 2026 |
   652→| TD-003 | Cache de ranking expira em 60s, deveria ser event-driven | Média | 30 SP | Q2 2026 |
   653→| TD-004 | Sem rate limiting em API pública | Alta | 20 SP | Q1 2026 |
   654→| TD-005 | Cobertura de testes em módulo de IA é 50% (meta 80%) | Média | 40 SP | Q2 2026 |
   655→| TD-006 | Console.log em produção em 12 arquivos | Baixa | 8 SP | Q1 2026 |
   656→| TD-007 | Sem migrations online (deploy causa downtime de 30s) | Alta | 60 SP | Q2 2026 |
   657→| TD-008 | Storybook desatualizado (30% componentes sem stories) | Baixa | 20 SP | Q2 2026 |
   658→| TD-009 | Sem ADRs para decisões de v1.0 (retroativo) | Média | 15 SP | Q1 2026 |
   659→| TD-010 | Bulkhead ausente (uma empresa grande pode degradar serviço) | Alta | 50 SP | Q2 2026 |

   711→# Capítulo 11 — Migration Paths Entre Versões
   712→
   713→Cada versão maior (v1.0 → v2.0 → ...) envolve breaking changes que precisam de migração cuidadosa para clientes existentes.
   714→
   715→## 11.1 Princípios de Migration
   716→
   717→1. **Backward compatibility:** nova versão deve funcionar com dados antigos
   718→2. **Progressive rollout:** 5% → 25% → 50% → 100% dos clientes
   719→3. **Automatic migration:** cliente não precisa fazer nada (sistema migra automaticamente)
   720→4. **Rollback capability:** se algo quebrar, voltar em < 5min
   721→5. **Communication:** clientes notificados 30 dias antes, com changelog
   722→6. **Beta program:** clientes voluntários testam antes do rollout geral
   723→
   724→## 11.2 v1.0 → v2.0 Migration
   725→
   726→### Breaking Changes
   727→
   728→- Auth: troca de NextAuth para solução própria — requer re-login de todos os usuários
   729→- Schema: tabela `results` particionada — migração online em janelas de baixo tráfego
   730→- API: versãoamento `/api/v1/` mantido, `/api/v2/` para novos endpoints
   731→
   732→### Plano de Migration
   733→
   734→```
   735→T-30 dias: Comunicado aos clientes (email + in-app)
   736→T-15 dias: Beta program aberto (voluntários)
   737→T-7 dias:  5% dos clientes migrados (canary)
   738→T-3 dias:  25% migrados
   739→T-1 dia:   50% migrados
   740→T+0:       100% migrados
   741→T+7 dias:  Encerramento v1.0 (end of life)
   742→```
   743→
   744→### Script de Migration
   745→
   746→```typescript
   747→// scripts/migrate-v1-to-v2.ts
   748→import { prisma } from '@/lib/prisma';
   749→
   750→async function migrateTenant(companyId: number) {
   751→  console.log(`Migrating company ${companyId}...`);
   752→  
   753→  // 1. Backup
   754→  await backupTenant(companyId);
   755→  
   756→  // 2. Migrate auth (force re-login)
   757→  await prisma.session.deleteMany({ where: { companyId } });
   758→  await prisma.refreshToken.deleteMany({ where: { companyId } });
   759→  
   760→  // 3. Partition results (online)
   761→  await partitionResultsTable(companyId);
   762→  
   763→  // 4. Update settings
   764→  await prisma.systemSettings.updateMany({
   765→    where: { companyId },
   766→    data: { version: '2.0.0' },
   767→  });
   768→  
   769→  console.log(`Company ${companyId} migrated successfully`);
   770→}
   771→
   772→async function main() {
   773→  const companies = await prisma.company.findMany({ where: { active: true }});
   774→  for (const company of companies) {
   775→    try {
   776→      await migrateTenant(company.id);
   777→    } catch (err) {
   778→      console.error(`Failed to migrate ${company.id}:`, err);
   779→      await rollbackTenant(company.id);
   780→    }
   781→  }
   782→}
   783→
   784→main();
   785→```

   841→| Closed Beta → Open Beta | 0 bugs P0/P1, CSAT > 80%, 20+ clientes testaram |
   842→| Open Beta → GA | 0 bugs P0/P1/P2, CSAT > 85%, 100+ clientes, 30 dias estável |

   851→4. **Incentivo:** desconto de 10% por 3 meses para participantes ativos

   853→### Onboarding Beta
   854→
   855→```
   856→1. Cliente aceita termo de beta (riscos, suporte limitado)

   861→6. Check-in semanal do CSM
   862→```

   864→### Coleta de Feedback

   866→- **In-app feedback widget:** "Como avalia esta feature?" (1-5 estrelas + comentário)
   867→- **Survey NPS da feature:** após 30 dias de uso
   868→- **Entrevistas qualitativas:** 5 clientes por mês, 30min cada
   869→- **Telemetria:** uso real (queries, ações, fluxos)
   870→- **Bugs reportados:** via Sentry + Linear

   872→### Decisão de GA

   922→## 13.2 Processo de Feedback Loop
   923→
   924→```
   925→1. Coleta (múltiplas fontes)
   926→2. Triagem (PM + CSM + Support lead, semanal)
   927→3. Categorização (bug, feature request, improvement, complaint)
   928→4. Priorização (RICE scoring)
   929→5. Planejamento (sprint planning, quarterly)
   930→6. Implementação
   931→7. Comunicação ("você pediu, nós fizemos")
   932→8. Medição de impacto (uso da feature, NPS delta)
   933→```
   934→
   935→## 13.3 Ferramentas
   936→
   937→- **Linear:** bugs e feature requests
   938→- **Productboard:** product feedback aggregation
   939→- **Vitally:** customer health + NPS
   940→- **Slack:** canais `#feedback` e `#feature-requests`
   941→- **Notion:** entrevistas e notes de calls
   942→- **Zoom:** gravações de entrevistas (com transcrição)
   943→
   944→## 13.4 Comunicação "You Asked, We Built"
   945→
   946→Toda feature implementada baseada em feedback deve ser comunicada:
   947→
   948→1. **Email para quem pediu:** "Você pediu X em [data], está pronto!"
   949→2. **Release notes:** destacar "Baseado em feedback de N clientes"
   950→3. **In-app notification:** banner na primeira vez que abre
   951→4. **Blog post:** para features maiores
   952→5. **Social media:** para features de destaque
   953→
   954→## 13.5 Métricas de Feedback Loop
   955→
   956→| Métrica | Alvo | Como Medir |
   957→|---------|------|------------|
   958→| Time to acknowledge feedback | < 48h | Linear |

  1557→# Capítulo 19 — Decision Framework
  1558→
  1559→## 19.1 RICE (Reach, Impact, Confidence, Effort)
  1560→
  1561→Toda feature candidata é avaliada:
  1562→
  1563→- **R**each: quantos usuários impacta (por trimestre)
  1564→- **I**mpact: magnitude do impacto (3=muito, 2=médio, 1=baixo, 0.5=mínimo)
  1565→- **C**onfidence: confiança na estimativa (100%, 80%, 50%)
  1566→- **E**ffort: meses-pessoa necessários
  1567→
  1568→**Score = (R × I × C) / E**
  1569→
  1570→### Exemplo Prático
  1571→
  1572→| Feature | Reach | Impact | Confidence | Effort | Score |
  1573→|---------|-------|--------|------------|--------|-------|
  1574→| IA sugerir metas | 1000 | 3 | 80% | 2 | 1200 |
  1575→| App nativo iOS | 500 | 3 | 80% | 4 | 300 |
  1576→| Dark mode | 5000 | 1 | 100% | 0.5 | 1000 |
  1577→| Multi-moeda | 200 | 2 | 80% | 1.5 | 213 |
  1578→| BI cubos OLAP | 300 | 3 | 50% | 6 | 75 |
  1579→
  1580→Priorizar por score descendente.
  1581→
  1582→## 19.2 MoSCoW (Must, Should, Could, Won't)
  1583→
  1584→Para cada release:
  1585→
  1586→- **Must:** obrigatório, sem isto não lança
  1587→- **Should:** importante, mas pode esperar uma release
  1588→- **Could:** nice to have, se sobrar tempo
  1589→- **Won't:** explicitamente fora do escopo desta release
  1590→
  1591→### Exemplo v1.0
  1592→
  1593→- **Must:** Auth, Empresas, Usuários, Indicadores, Metas, Resultados, Ranking, Dashboard, Campanhas, Auditoria, Licenciamento
  1594→- **Should:** Backup, Atualizações, PWA, Painel admin
  1595→- **Could:** Tema customizado por empresa, multi-idioma parcial
  1596→- **Won't:** IA, Marketplace, Apps nativos, BI
  1597→
  1598→## 19.3 Kano Model
  1599→
  1600→Classifica features por tipo de necessidade:
  1601→
  1602→| Tipo | Descrição | Exemplo |
  1603→|------|-----------|---------|
  1604→| **Must-be** (básicas) | Ausência causa insatisfação; presença não causa satisfação | Login, CRUD básico, segurança |
  1605→| **One-dimensional** (performance) | Mais é melhor | Velocidade, número de integrações |
  1606→| **Attractive** (excitement) | Surpreende; ausência não frustra | IA insights, ranking em tempo real |
  1607→| **Indifferent** | Não importa | Features que ninguém usa |
  1608→| **Reverse** | Mais é pior | Anúncios no app |
  1609→
  1610→### Mapeamento Orion
  1611→
  1612→| Feature | Tipo Kano |
  1613→|---------|-----------|
  1614→| Login | Must-be |
  1615→| Multi-tenant | Must-be |
  1616→| Auditoria | Must-be |
  1617→| Velocidade API | One-dimensional |
  1618→| Número de integrações | One-dimensional |
  1619→| IA sugerir metas | Attractive |
  1620→| Gamificação | Attractive |
  1621→| Analytics Network | Attractive |
  1622→| Anúncios | Reverse (não faremos) |
  1623→
  1624→### Estratégia
  1625→
  1626→- **Must-be:** sempre ter, sem nunca falhar
  1627→- **One-dimensional:** investir continuamente para melhorar
  1628→- **Attractive:** 1-2 por release, para encantar
  1629→- **Indifferent:** cortar do roadmap
  1630→- **Reverse:** nunca fazer
  1631→
  1632→## 19.4 Processo de Decisão Combinado
  1633→
  1634→```
  1635→1. Brainstorm features (qualquer um pode propor)
  1636→2. Score RICE para cada uma
  1637→3. Categorizar MoSCoW baseado em estratégia e timing
  1638→4. Classificar Kano para balancear (não só Must-be)
  1639→5. Mix final: 60% Must/Should (RICE alto) + 30% Could (Kano Attractive) + 10% Won't explícito
  1640→6. Validate com 5 clientes (entrevistas)
  1641→7. Ajustar com base no feedback
  1642→8. Planejar nas sprints
  1643→```
  1644→
  1645→## 19.5 Critérios de Go/No-Go
  1646→
  1647→Antes de iniciar uma feature:
  1648→
  1649→| Critério | Pergunta | Required |
  1650→|----------|----------|----------|
  1651→| Estratégia | Está alinhada com visão 5 anos? | Sim |
  1652→| Demanda | Tem 5+ clientes pedindo? | Sim |
  1653→| Viabilidade técnica | Sabe como fazer? | Sim |
  1654→| Recursos | Tem devs disponíveis? | Sim |
  1655→| ROI | LTV/CAC > 3× ou churn reduz? | Sim |
  1656→| Risco | Pode quebrar algo crítico? | Não |
  1657→| Compliance | Atravessa LGPD? | Não |
  1658→- Suporte | Consegue treinar CS/suporte? | Sim |
  1659→| Manutenção | Consegue manter pós-launch? | Sim |
  1660→| Documentação | Consegue documentar? | Sim |
  1661→
  1662→Se todos "Sim/Não": **GO**. Qualquer "Não": **No-Go** ou **Defer**.

  1948→# Conclusão
  1949→
  1950→O roadmap do Projeto Orion é ambicioso mas executável. A chave do sucesso está em:
  1951→
  1952→1. **Foco** — não tentar fazer tudo em v1.0
  1953→2. **Validação** — cada feature testada com clientes reais antes de escalar
  1954→3. **Velocidade** — ship frequentemente, itere com base em dados
  1955→4. **Excelência técnica** — não acumular débito técnico que atrapalhe versões futuras
  1956→5. **Ecossistema** — marketplace e API criam lock-in positivo
  1957→6. **Pessoas** — time excepcional com cultura forte
  1958→7. **Disciplina financeira** — break-even em 2026, lucro em 2027+
  1959→8. **Customer obsession** — ouvir, comunicar, encantar
  1960→
  1961→O Orion não é apenas um software, é uma plataforma de negócios que deve evoluir por décadas. Cada decisão hoje deve considerar impacto em 5 anos.
